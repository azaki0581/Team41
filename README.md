## 2. 파일 구조

```
냉장고 털기/
├─ index.html      ← 앱 전체 (화면 + 추천 로직). 여기만 고치면 화면이 바뀝니다
├─ recipes.js      ← 레시피 1,151건. 자동 생성물이라 직접 고치지 마세요
├─ README.md       ← 지금 이 문서
├─ vercel.json     ← 배포용 보안 헤더. 로컬 실행에는 영향 없음 (7번 참고)
│
├─ data/
│  └─ raw-cookrcp01.json    식약처 API 응답 원본 (보존용, 4.2MB)
│
└─ tools/                   recipes.js 를 만드는 스크립트
   ├─ fetch-recipes.ps1     API 원본 수집   (한 번만 실행)
   ├─ build-recipes.ps1     원본 → recipes.js 가공
   └─ rules.json            재료 이름 통일, 양념 분류 등 모든 규칙
```

**어디를 고쳐야 하나요?**

| 하고 싶은 것 | 고칠 파일 |
|---|---|
| 화면 디자인, 문구, 추천 순서 | `index.html` |
| 재료 이름이 갈라져 나올 때 (예: 달걀/계란) | `tools/rules.json` → 그 다음 `build-recipes.ps1` 실행 |
| 기본으로 켜둘 양념 목록 | `tools/rules.json` 의 `pantryStaples` |
| 조리시간 추정 기준 | `tools/rules.json` 의 `verbMinutes` |

`tools/rules.json` 은 항목마다 `_` 로 시작하는 설명 키가 붙어 있으니 그걸 읽고 고치면 됩니다.

## 3. 이 서비스가 하는 일

### 핵심 기능 (MVP)

1. **재료 입력** — 태그(칩) 추가/삭제, 자주 쓰는 재료 16종 빠른 추가, 양념·조미료 24종 체크
2. **레시피 추천** — 가진 재료로 만들 수 있는 순서로 정렬
3. **조리 가이드** — 정확한 계량, 단계별 사진, 조리 순서, 영양정보

### 카드의 약속은 하나뿐 — "지금 이걸 만들 수 있나?"

부족한 주재료와 따로 사야 하는 양념을 **하나로 합쳐서** 판정합니다.

| 사야 할 것 | 배지 | 안내 |
|---|---|---|
| 0개 | `바로 만들 수 있어요` (초록) | 없음 |
| 1–2개 | `2개만 더 있으면 돼요` (주황) | 🛒 `양배추, 보리새우만 있으면 완성돼요.` |
| 3개 이상 | `내 재료 71%` (중립) | 🛒 `밀가루, 빵가루, 칠리소스가 더 필요해요.` |

> 처음에는 주재료와 양념을 나눠 표시했습니다. 그랬더니 배지는 "재료 다 있어요"라고 해놓고 아래에서 "스리라차도 필요해요"라고 말하는 상황이 생겼습니다. 다 있다는 말을 믿고 요리를 시작한 사람에게는 배신입니다. **우리 쪽 분류는 사용자의 관심사가 아닙니다.**

배지가 `바로 만들 수 있어요` 라고 하면 정말로 아무것도 살 게 없습니다.

### 양념 · 조미료는 사용자가 직접 고릅니다

양념을 매칭률에 넣으려면 "이 사람이 간장을 갖고 있는가"를 알아야 합니다. 예전에는 우리가 정해놓고 통보했지만("기본 양념은 있다고 보고 찾았어요"), 지금은 그 가정을 화면으로 꺼내 사용자가 켜고 끕니다.

- 사용 빈도순 **24종**을 보여줍니다 (마늘 478회 → 매실청 26회)
- `pantryStaples` 는 **켜진 채** 시작 — 없는 것만 끄면 되니 첫 사용에 부담이 없습니다
- 올리브유·버터·다시마·마요네즈처럼 집집마다 다른 것은 **꺼진 채** 시작
- 물·얼음(`alwaysHave`)은 목록에 띄우지 않고 항상 있는 것으로 계산
- 선택은 `localStorage` 에 저장됩니다 (부엌 사정은 매번 바뀌지 않으니까 — 재방문율 KPI에도 도움)

### 추천 순서

```
1순위  지금 당장 만들 수 있는가 (사야 할 것 0개)
2순위  점수 = 내 재료 사용 수 × 3  −  사야 할 것 × 2  −  구하기 어려운 재료 × 4
```

- **내 재료를 많이 쓸수록 가산** — 이 서비스는 냉장고를 '터는' 게 목적입니다. 여기서 "내 재료"는 **입력창에 직접 담은 재료만** 셉니다. 체크해 둔 양념 17종과 물은 빠집니다.
- **구하기 어려운 재료는 크게 감점** — 데이터 전체에서 5회 미만 등장하는 재료(락교·머위대)는 사러 가기도 어렵습니다.

**내 재료를 하나도 안 쓰는 요리는 결과에서 뺍니다.** 아무리 만들기 쉬워도 그건 냉장고 털기가 아닙니다. (그렇게 걸러서 남는 게 하나도 없을 때만 범위를 넓힙니다 — 빈 화면보다는 나으니까요.)

사야 할 것이 3개 이하(`MAX_NEED`)인 레시피만 결과에 넣고, 그중 살 게 없는 것의 개수를 제목에 씁니다. `만들 수 있는 요리 660개` 처럼 숫자를 부풀리지 않습니다.

> **2026-08-17 수정 전에는 이렇지 않았습니다.** 정렬 1순위가 "사야 할 재료 수" 하나뿐이었고, 점수는 3순위 타이브레이크로만 쓰였습니다. 그런데 "가진 재료"에 켜둔 양념 17종과 물이 전부 포함되다 보니, *양념만으로 되는 요리 + 모르는 재료 1개*가 *내 재료를 3개 다 쓰지만 2개 더 사야 하는 요리*를 언제나 이겼습니다. 계란·김치·밥으로 돌리면 상위 20개 중 내 재료를 하나라도 쓰는 게 4개(20%)뿐이었고, 1·2·3위는 전부 0개였습니다. 바로 위에서 "이걸 빼면 1순위로 올라온다"고 경고해 둔 매운락교무침이 실제로 10위 안에 있었습니다. 기준을 "가진 재료"에서 "내 재료"로 바꾸고 점수를 1순위로 올려서 고쳤습니다. (같은 조건에서 지금은 새송이등갈비·콩나물부추볶음처럼 내 재료를 4개씩 쓰는 요리가 상위에 옵니다.)

## 4. 레시피는 어디서 왔나

[식품의약품안전처 「조리식품의 레시피 DB」(COOKRCP01)](https://www.data.go.kr/data/15060073/openapi.do) 공공데이터입니다.

정확한 계량(`연두부 75g(3/4모)`), 단계별 조리 사진, 영양정보, 나트륨 저감 조리 팁이 모두 원문 그대로 들어갑니다. 화면과 푸터에 출처를 명시합니다.

**API 를 실행 중에 부르지 않습니다.** 한 번 받아서 `recipes.js` 에 넣어뒀기 때문에 — 인증키가 배포본에 노출되지 않고, 호출 비용도 없고, 식약처 서버가 멈춰도 앱은 돌아갑니다.

### 원본에 없는 값 — 조리시간과 작업량

공공 DB에도 **조리시간·난이도 필드는 없습니다.** 아래 방식으로 계산하되 화면에는 결과만 보여줍니다.

| 항목 | 산출 방식 | 화면 표시 |
|---|---|---|
| **조리시간** | 문장에서 "10분 정도 찐다" 같은 시간을 추출해 합산. 없는 단계는 조리 동작(볶기 4분, 끓이기 6분)으로 추정 | `⏱ 15~22분` — 범위로 표시해 어림값임을 전달 |
| **대기시간** | 불리기·재우기처럼 손을 대지 않는 시간은 분리 | `+대기 30분` |
| **작업량** | "난이도"(요리 실력)는 데이터로 알 수 없어 표시하지 않음. 대신 단계 수·재료 종류·지시문 분량·실패 위험 과정으로 계산 | `🧑‍🍳 간단 / 보통 / 손 많이 감` |

조리 단계에는 시간·불세기 배지를 달지 않습니다. 원문 문장에 이미 "중간 불에서 10분 정도 찐다"처럼 들어 있어 중복이기 때문입니다.

## 5. 디자인

**당근 SEED Design System** 토큰을 적용했습니다. ([카탈로그](https://getdesign.kr/services/seed-design) · [저장소](https://github.com/CaesiumY/ko-design-md))

기획서 2-3의 "design.md 파일을 반영해서 디자인을 바꿔줘" 항목에 해당합니다. SEED를 고른 이유는 브랜드 컬러 `carrot-600 #ff6600` 이 기획서의 "따뜻한 색상(오렌지·크림·화이트 계열)" 요구와 맞고, 카드+칩+필터바 패턴이 이 서비스 구조와 그대로 맞기 때문입니다. (배달의민족도 검토했으나 브랜드 컬러가 민트라 제외)

| 항목 | 값 |
|---|---|
| 팔레트 | carrot 100–900, gray 00–1000, green 100/300/700/900 — 라이트·다크 양쪽 원본 hex 그대로 |
| 서체 | **별도 브랜드 서체 없음.** SEED `font-sans` 토큰(시스템 폰트 스택) 원문 그대로 |
| 타이포 | t1–t14 (11/15 … 48/60). h1=t13, 요리명=t7, 본문=t5, 캡션=t3. 굵기는 400/500/700만 |
| 간격 | 4px 기반, 거터 16px(base) / 32px(md 768+) |
| 라운드 | r1(4) … r6(24), CTA·칩은 `full` |
| 그림자 | 깊이는 면(surface) 레이어로 표현하고 그림자는 아낌 |
| 모션 | d1(50ms)–d6(300ms), 누를 때 scale 0.98 |
| 다크모드 | 전체 지원 (`prefers-color-scheme`) |

> **서체** — SEED에는 당근이 따로 만든 글씨체가 없습니다. 원문에 *"별도 브랜드 서체 없음 — 여러 국가·문화·OS에서 일관된 경험과 가독성을 위해 기기 시스템 폰트 사용"* 이라고 명시돼 있어, 시스템 폰트를 쓰는 것이 곧 SEED를 따르는 것입니다.

**다크모드 구현** — SEED 원칙은 *"팔레트가 뒤집히고 역할 토큰 참조는 그대로 유지된다"* 입니다. 팔레트 변수만 다크 값으로 재정의하면 나머지가 자동으로 따라옵니다. 단계 이동이 필요한 건 브랜드 솔리드 하나뿐(carrot-600 → 700)입니다.

**접근성 (APCA)** — SEED 기준은 Lc 75 이상입니다. 텍스트 23곳을 실측해 맞췄습니다. 글자에는 900 단계, 면을 채우는 데는 600/700 단계를 씁니다. 브랜드색 위의 글자는 테마와 무관하게 흰색이어야 하므로 `static-white` 토큰을 씁니다. 예외 1곳 — CTA 버튼(흰 글씨 on `carrot-600`)은 Lc 60이지만 SEED가 규정한 브랜드 버튼 조합 그대로이고 16px 이상 굵은 글씨는 APCA 허용 범위입니다.

> **라이선스** — SEED 소프트웨어는 Apache 2.0입니다. 이 프로젝트는 **토큰과 컴포넌트 규칙만** 가져다 썼고, 당근의 로고·워드마크나 매너온도 같은 제품 고유 개념은 쓰지 않았습니다. 시스템 이름(SEED)을 사용자 화면에 노출하지 말라는 규정도 지켜, 출처 표기는 이 문서에만 둡니다.

## 6. 레시피 데이터 갱신하기

평소에는 할 필요 없습니다. 식약처가 레시피를 추가했을 때만 하면 됩니다.

```powershell
# 1) 인증키 발급 (무료·즉시)
#    https://www.foodsafetykorea.go.kr/apiMain.do → OpenAPI 인증키 신청

# 2) 원본 수집 (1분 이내)
.\tools\fetch-recipes.ps1 -ApiKey "발급받은인증키"

# 3) 앱용 데이터 생성
.\tools\build-recipes.ps1
```

가공 규칙(`rules.json`)만 고칠 때는 **3번만** 다시 돌리면 됩니다. API 재호출이 필요 없습니다.

> ⚠️ **인증키는 파일에 저장하지 마세요.** 명령줄 인자로만 넘깁니다. 생성물에는 키가 들어가지 않으므로 GitHub 에 올려도 노출되지 않습니다.
>
> ⚠️ `tools/*.ps1` 을 편집할 때는 **UTF-8 BOM** 으로 저장하세요. Windows PowerShell 5.1 은 BOM 없는 파일을 ANSI로 읽어 한글이 깨집니다.

3. **수정 반영** — `"수정사항 반영하고 커밋해줘"` → Vercel 자동 반영

조리 사진은 식약처 서버에서 https로 불러옵니다 (mixed content 문제 없음).

### 보안 (2026-08-17)

`index.html` 맨 위에 **CSP(Content-Security-Policy)** 를 넣어, 이 페이지가 무엇을 불러올 수 있는지 브라우저에 못박아 뒀습니다. 기본은 전부 차단(`default-src 'none'`)이고, 조리 사진(식약처 도메인)·파비콘(`data:`)만 열려 있습니다. `connect-src 'none'` 이라 이 앱은 어디로도 데이터를 보낼 수 없습니다 — 입력한 재료와 별점이 브라우저 밖으로 나가지 않는다는 걸 코드가 아니라 브라우저가 보장합니다.

`script-src` 에 `'unsafe-inline'` 이 남아 있는 건 앱 전체가 `index.html` 한 파일 안의 `<script>`·`<style>` 로 되어 있기 때문입니다. 이걸 없애려면 JS/CSS를 별도 파일로 빼야 하는데, "index.html만 고치면 화면이 바뀐다"는 이 프로젝트의 구조를 깨는 일이라 하지 않았습니다.

클릭재킹 방어(`frame-ancestors`)는 `<meta>` 태그로는 적용되지 않고 실제 HTTP 응답 헤더여야 합니다. 그래서 프로젝트 루트에 **`vercel.json`** 을 넣어뒀습니다 — 배포하면 자동으로 적용되고, 로컬에서 `index.html` 을 더블클릭할 때는 아무 영향이 없습니다.

그 밖에 함께 손본 것:

- `escapeHtml()` 이 작은따옴표(`'`)를 빠뜨리고 있었습니다. 지금은 속성값을 전부 큰따옴표로 감싸고 있어서 당장 문제는 없지만, 나중에 누가 속성 하나를 작은따옴표로 쓰는 순간 조용히 구멍이 되는 자리라 막아뒀습니다.
- `localStorage` 값을 읽을 때 타입까지 확인합니다(`readStored()`). 예전에는 `JSON.parse` 만 `try` 로 감싸서, 파싱은 됐는데 기대와 다른 타입이면(배열 자리에 숫자 등) 그 다음 줄에서 터져 앱 전체가 멈췄습니다.

## 9. 다음 단계

기획서 1-7의 반복 개선 계획을 기준으로:

- **2차** — 재료 입력 자동완성(1,660종에서 추천), 재료 별칭 사전 보강, 대체 재료 제안

- AI 연동은 **레시피 생성이 아니라 추천 로직에만** 적용할 것. 생성형은 출처가 없어 신뢰성을 떨어뜨립니다.

### KPI

| 지표 | 목표 | 현재 |
|---|---|---|
| 재료 입력 → 추천까지 소요 시간 | 3초 이내 | **16~25ms** ✅ |
| 추천 레시피 클릭률 | 60% 이상 | 배포 후 측정 |
| 재방문율 (1주일 내 재사용) | 30% 이상 | 배포 후 측정 |

결과 화면 우측 상단에 실제 추천 소요 시간이 표시되어, 시연에서 첫 번째 KPI를 그대로 보여줄 수 있습니다.

> **이 숫자는 계산 시간만입니다.** 사용자가 실제로 체감하는 시간은 여기에 로딩 연출 0.7초(`LOADING_MS`)가 더해진 값입니다.
>
> 2026-08-17 이전에는 `setTimeout(…, 700)` **안에서** 시간을 재고 있어서, 화면에 뜨는 값이 무엇을 입력하든 항상 "0.7초"였습니다. 연출 시간을 추천 속도라고 보여준 셈이라 KPI 근거로 쓸 수 없었습니다. `search()` 앞뒤만 재도록 고쳤고, 1초 미만은 `0.0초` 대신 ms 로 표시합니다.
